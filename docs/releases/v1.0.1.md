# Exoma 1.0.1

Release candidate preparation. The version and documentation are prepared for 1.0.1;
final-candidate validation, staging, tagging and publication remain separate release steps.
This page does not declare the candidate ready to tag.

The changes since 1.0.0 include Codex host integration, runtime hardening, a higher Python
minimum, and clearer research and measurement boundaries.

## Compatibility and upgrading

**Python 3.11 or newer is required. Python 3.10 support has been removed.** This is a
breaking environment requirement despite the intended patch version. The package metadata,
entry-point guards, hook interpreter selection and CI now use the new minimum.

An installation running under Python 3.10 must move to a supported interpreter before it
can use this release. `exoma update` stays in its current Python environment; it does not
perform that migration. After installing Exoma under Python 3.11+, run `exoma install`
from that installation and `/.upgrade` in each project to refresh pinned interpreter
paths and generated runners. See [installation and migration](../installation.md).

## Codex host context

- Selecting Codex as a primary host now automatically installs Exoma's task-scoped context
  in `auto_review.extra_policy`, including on noninteractive updates. An explicit
  `--no-codex-auto-review-context` opt-out persists; `--codex-auto-review-context` clears it.
  Legacy boolean-only off states migrate to the automatic default.
- The installer merges its owned TOML block while retaining user policy and deny rules.
  Installation checks, rollback and uninstall account for that ownership. Edited owned
  blocks are reported rather than silently overwritten.
- Reviewer context is an instruction to the host reviewer, not an enforced read boundary
  or a guarantee of approval. Runner permissions follow the active host policy, and a
  denied action must not be retried through a workaround. Installed Codex hooks still need
  review and trust through `/hooks`.

See [Codex reviewer context](../reference.md#codex-auto-review-context) and
[security boundaries](../security.md).

## Runtime and verification

- Execution approval binds the plan revision, scope and runtime session. Re-recording a
  plan revokes earlier approval; forked and concurrent sessions retain separate authority.
- Provider capture, worker recovery, evidence freshness, atomic writes and bundle
  integrity checks have additional validation and regression coverage. Mutation detection
  reports unavailable checks rather than treating incomplete inspection as proof of no
  change; its observation limits remain documented.
- Verification preserves findings and their routing. Test reuse requires a matching
  content identity; unreadable or unavailable fingerprint inputs do not establish a
  reusable pass. Runtime-derived verdicts remain distinct from final primary-agent
  acceptance and substantive task correctness.
- Literal command data and direct commit requests have additional policy regression
  coverage, including native parser and gate cases. Source and isolated integration
  coverage do not establish deployed-hook behavior.

See [runtime contracts](../runtime-contracts.md), [reference](../reference.md) and
[limitations](../limitations.md).

## Research and measurement

- The README describes agent-workflow as Exoma's research and staging companion for
  resource-aware agent decomposition. Context allocation remains a design hypothesis;
  delegation can add token usage, latency, coordination work and information loss.
- [Interpretation boundaries](../evaluation/metrics.md#interpretation-boundaries) distinguish
  runtime verification outcomes from final acceptance, token-difference proxies from
  counterfactual savings, session activity from human work time, and pattern-matched
  corrections from the full range of human intervention. Available metrics alone do not
  establish effectiveness.
- Since 1.0.0, the metric registry moved to version 2 and `runtime.provider_call@2` excludes
  evidence-reuse and avoided-provider rows. Historical figures retain their metric versions.
- The `outcome.context_saved@2` missing-data description now matches its existing producer:
  rows without provider counts add no fresh input and mark the task partial; estimated
  returned output is still subtracted, and fallback is confined to the separate badge
  figure. This clarification changes no calculation or metric version.

## Staging evidence and its limits

The companion [handoff receipt](https://github.com/dammar01/agent-workflow/blob/main/docs/evaluation/exoma-handoff-2026-11-10/README.md)
identifies source `a965cf20bce03015cdf0f56952eb6c45e30cbfa4`, before this release
preparation. Its source checks were executed on Windows on 2026-11-10; publication of the
sanitized receipt on 2026-11-11 was not another execution.

- Reported source results: portable parser/gate suite 16/16; `codex-host`,
  `execution-chain`, `verify-reuse` and `metrics-contract` exited zero.
- `verify-runtime-tests` initially failed because `AGENT_HOME` hid its temporary-home
  fixture; the disposable-home recheck exited zero without source or assertion changes.
- Real-provider E2E and deployed-hook behavior are not established for that SHA by this
  receipt. Earlier DEC-084 provider results belong to `1071c2f` and cannot be transferred
  to `a965cf20` or the final 1.0.1 candidate.
- Raw execution logs remain private. These are reported historical results, not an
  independent recount or evidence that all release gates passed.

## Final-candidate release checklist

No final-candidate SHA or complete release receipt is recorded here yet. Follow
[RELEASE.md](../../RELEASE.md); record outcomes against the exact final commit.

- [ ] Review the Python compatibility change and release notes before publication.
- [ ] Check version stamps, manifest and lock; run the source suites and local E2E.
- [ ] Run real-browser and real-provider E2E; record any explicit skip and its coverage limit.
- [ ] Confirm CI and clean wheel/sdist smoke checks, including the supported OS/Python matrix.
- [ ] Record real use and the extent of deployed-hook validation without inferring it from
  source tests.
- [ ] Stage the same final SHA in agent-workflow, including its harnesses, research-record
  integrity checks, and delegated E2E. Any fix creates a new candidate requiring staging
  again. Successful scientific validation or an answered research question is not required;
  see the [Development and Research Relationship](../development.md#development-and-research-relationship).
- [ ] Check remote tag/package availability and tag-to-package version consistency.
- [ ] Tag only the candidate accepted through the engineering release gates. Pushing the
  tag triggers PyPI publication; verify reproducibility from a clean checkout afterward.
