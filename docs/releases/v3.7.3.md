## `/.verify-browser` fixes

- **A draft no longer fails on the first attempt because of its shape.** An `[E2E SPEC]` section
  that arrives but fails validation (scenario outside the ```` ```json ```` fence, broken JSON, values
  outside the enum such as `side_effect`, stale selector key, policy/grounding rejection) gets
  ONE repair in the same provider thread, quoting the validator message, and the reply is
  revalidated from scratch. Previously only a missing section was re-requested; a broken
  section went straight to `spec_invalid`. The draft prompt now names the valid `side_effect` values and
  the fence rule. `meta.e2e.repair` = `{attempted, errors, recovered}`; without a
  `provider_session_id` it records `reason: no_provider_session`. Evidence: of 39 drafts across
  16 sessions (2026-09-21..27) not a single one was `ready` — 34 `invalid`, 5 `blocked`; the most frequent
  first errors were broken JSON (10), claims without `source_refs` (9), selector shape (6)
  (`docs/research/real-cases/CASE-005-…`, decision DEC-006; `core/evidence/e2e/spec.py`,
  `runner.py`, `core/prompt/prompt_builder.py`).
- **`repeat_failure` without a new session.** Each counted failure stores a project fingerprint
  (HEAD + diff + untracked files, outside `.workflow/`; `core/evidence/e2e/fingerprint.py`).
  A streak at the limit whose fingerprint differs from the current project is released and the run proceeds
  (`meta.e2e.repeat_released.by = change_detected`). Editing the scenario does not count as a
  change. When the brake refuses, the event is recorded as `repeat_failure` knowledge that is
  offered to the next draft across sessions and retires after one `pass` run. A fix
  without file changes still goes through `ignore_repeat_brake` once. The `verify-browser` skill
  stops suggesting a new session.
- **The `repeat_failure` brake distinguishes app failures.** The `app` bucket streak now only
  increments when the failure signature is the same: page (normalized `url_after`, query and
  ids folded), field (step selector from the placeholder scenario), and condition (error type,
  step expectation, unmet readiness) — `classify.failure_signature`, `v1:<digest>`.
  Three different login failures (form not yet rendered, redirect held by the runtime, that same
  redirect again) used to be counted as one streak and refused the 4th run. `timeout`/`harness` stay coarse.
  Each outcome records `runtime` (`TOOL_VERSION` + digest of `core/evidence/e2e/*.py`); streaks
  from another runtime are released (`repeat_released.by = runtime_changed`). Old `app` records without
  a signature are read as having no streak. `repeat_failure` knowledge has one entry per signature.
  Decision DEC-008 (partially revises DEC-005).
- **Player polling no longer holds back browser events.** Wait loops (selector resolution,
  readiness, `expect_url`/`expect_title`) now wait via `page.wait_for_timeout`, not
  `time.sleep`. Sync Playwright only dispatches events (write-guard route handler,
  `framenavigated`) while the thread is inside a Playwright call; `time.sleep` and
  `page.url` (a cached attribute) are not such calls, so a login POST passing through the guard was held
  until `expect_url` failed — its duration was always ≈ `step_timeout_ms` + 0.8 s, whatever the
  timeout. Decision DEC-007; `core/evidence/e2e/browser.py` `Session.pause`; regression
  locked by `tests/checks/e2e_browser.py` `_check_polling_keeps_events_flowing`.
- **Zero console windows from the git fingerprint (Windows).** `fingerprint.py` called `git`
  without `hidden_run_kwargs()`, so a console-less worker popped up a cmd window that
  flashed on every call. The new `hidden-spawn` suite (`tests/checks/hidden_spawn.py`)
  rejects `subprocess.*` in `core/`, `adapters/`, `utils/` that does not hide the console.
- **`data-e2e` is the only test attribute (breaking).** The `testid` selector key is replaced by `e2e`
  (`[data-e2e="…"]`), the same attribute that tagging proposes. `testid`, `data-testid`,
  and `data-e2e` as keys are rejected with a message naming `e2e` (and are also repaired
  through the draft repair path above). The page probe reads `data-e2e`. Old knowledge entries
  with `testid` are no longer offered. Projects that rely on `data-testid` need to
  add `data-e2e` to their elements — the tag proposals from the next run do this.

## `/.verify-browser` becomes DELEGATED

Previously three layers disagreed: the bundle `CLAUDE.md` put it in the LOCAL registry and
its skill said "no pre-flight gate", the reference called it delegated, and the intent map
did not know it, so the `/.verify-browser` prefix was read as `verify`
(decision: `docs/research/decisions/DEC-001-verify-browser-delegated.yaml`).

- `dist/config/claude/CLAUDE.md`: added to the DELEGATED registry and the pre-flight gate; the three stages
  are described — second_agent writes the draft spec (stage 1) and reviews the evidence (stage 3),
  the runtime player (a runtime child process) runs Playwright (stage 2).
- `dist/config/claude/hooks/intent-map.json`: `verify-browser` in the delegated list, the prefix
  pattern fixed so it is not swallowed by `verify`, trigger phrases added.
- `dist/config/claude/skills/verify-browser.md`: flow reversed — write a minimal request,
  run the draft, interview only if the draft reports the target is not configured or
  unreachable. `config.json` is read by the runtime, not by main_agent before the run.
- `tools/maintain/sync_intent_map.py`: command names may contain `-`.
- `README.md`, `docs/reference.md`, `docs/runtime-contracts.md`: classification and stages
  made consistent.

Trade-off: main_agent no longer reads `config.json` before the first draft, so a project
that is not yet configured pays for one draft call before the interview.

## Additions before the tag, after `dd70afd`

Still 3.7.3 (not yet tagged). The "Release status" table above was run before these additions
and does not apply to them; their status is at the end of this section.

### `/.verify-browser`: literal secrets patched per value (DEC-009)

Credential values typed in directly — in the task, in the stage 1 draft, or in the `request.json`
that the main agent copied from the draft — are now looked up through the same lookup the
player uses, then turned back into `${NAME}`. `request.json` is rewritten on disk. The run still
proceeds (the player receives the same values) and is flagged per name: `meta.e2e.secret_literals` +
`config_warnings`. A `fill` into a password field without a placeholder → `spec_invalid`. Details:
`docs/runtime-contracts.md`, "Literal credentials in agent-written input".

### `/.verify-browser`: `scenario` origin and structured diagnosis (DEC-010)

- A guessed selector that misses, a write/navigation rejected by the run policy → origin `scenario`,
  run `incomplete: scenario_error`: not retried, not counted by the 3x brake, does not clear
  an existing streak.
- Every non-pass run and every brake refusal carries `meta.e2e.diagnosis`
  (`cause`, `next_step`, `failed`, `fix_hint`, `reusable`) — also in `report.json`, the reviewer evidence
  block, and the quality line. Causes the next draft can use are stored
  as `failure_hint` knowledge.
- Drafts: validator errors are mapped to categories (`spec.error_category`), non-ready drafts
  carry a diagnosis, and every draft writes a `kind: e2e_draft` line; `--command report`
  summarizes them under `e2e.drafts`. Fake player: `harness_fail` mode is now a driver error,
  new `scenario_fail` for guessed selectors.

### Research, CHANGELOG, benchmark (DEC-011)

- Research records become YAML with a fixed schema (`docs/research/schema.yaml`, enums, per-type
  rules) checked by `tools/maintain/check_research.py` in the suite (`research`) and CI.
  A DEC must name its commit; H/EXP have no commit. Tracked records had their content converted as
  is; commits that were `unknown` were filled from Git (`dd70afd`). The README inventory
  is generated. PyYAML becomes a development dependency (`requirements-dev.txt`), the runtime stays
  stdlib-only.
- `CHANGELOG.md` becomes an index; per-version notes in `docs/releases/`.
- `bench/` removed; the benchmark method is recorded as H + EXP. That harness never
  produced a ledger, so no results were lost; `docs/evaluation/benchmark.md`
  explains this and points to commit `dd70afd` to see it again.

### Real-use findings before the tag

The additions above were tested on the maintainer's private web project (8 jobs: 4 drafts, 4 runs, headed
Chromium). Findings and their fixes, all before the tag:

- The literal-secret scrub was too aggressive at first: a profile password that is a common word
  turned step id `fill-password` into `fill-${E2E_PASS}` (false leak report, invalid
  draft), then the selector `#password`. Now structural fields (`id`, `claim_id`, …) are never
  scrubbed, a match inside a string must stand as a token, and in selector fields a
  purely alphabetic value is only matched whole. The player event scrubber also no longer
  changes `step_id`.
- A source-provenance selector that matched two elements (the password field and a show/hide button
  with the same label) was still classified `app` → verdict `fail` and entered the brake streak —
  the complaint DEC-010 answered, repeated. Now `selector_ambiguous`, whatever its provenance,
  has origin `scenario` with its own cause (`scenario_selector_ambiguous`); previously
  its diagnosis was mislabeled `selector_not_rendered`.
- Final result: draft ready without repair, without false leak flags; login + dashboard run 7/7
  passed (browser `pass`); the profile username value does not appear in any file in the session folder.
- Not yet closed (escalation, pre-existing before 3.7.3): the raw provider reply archives
  (`response.last.md`, `output.raw.md`) are written before the scrub.
