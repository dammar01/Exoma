# Exoma 1.1.1

Candidate preparation for an updater fix release. Commit, tagging and publication remain
separate release actions; this page does not declare the candidate ready to publish. The
`v1.1.0` tag and its notes ([v1.1.0](v1.1.0.md)) are retained.

## Changes

- **Orphan startup admission.** Package updates and workspace upgrades share a conservative
  admission decision. After the startup grace, a reservation whose owner is provably gone
  can be retired under the capacity/job guards before mutation. The terminal record prevents
  a late worker from reviving it. A live or unverifiable owner, malformed proof, pending
  cancellation or unconfirmed cleanup still refuses admission; ordinary recovery/liveness
  semantics are unchanged.
- **Controlled workspace refusal.** Invalid or unreadable cleanup records now give an update
  refusal with diagnostic context and exit 1 before package-manager selection, instead of
  an uncaught admission exception. Corrupt records never authorize mutation.
- **Asynchronous update contract.** An accepted handoff returns exit 3 before completion;
  use the reported observer/cancel arguments and subsequent `exoma update --status` to
  inspect the outcome. See the [runtime contracts](../runtime-contracts.md).
- **macOS guardian cleanup.** On Darwin the final group SIGKILL can return EPERM when the
  group holds only the already-exited, unreaped leader, which previously forced
  `cleanup_failed(signal_kill)` and an unconfirmed cleanup even after a successful reap.
  The failure is now deferred and discarded only when the child's exit was observed before
  the signal, the reap succeeded, and a following signal-0 probe of the group raises
  ESRCH. A present group, a denied or failed probe, a failed reap, a missing exit
  observation, or any non-EPERM signal error keeps the negative receipt. Signal 0 is the
  only signal sent after the reap. Contract: [docs/runtime-contracts.md](../runtime-contracts.md)
  and [docs/reference.md](../reference.md).
- **Windows transition coverage.** Every dist matrix cell runs a real A-to-B transition.
  GitHub-hosted Windows uses a disposable contained fixture: only its copied launcher
  and worker guards are adjusted for the inherited runner job. Reports explicitly mark
  `mode=contained`, `independent_worker_verified=false` and `release_acceptance=false`.
  Missing, stale, dirty or incorrectly scoped reports fail the CI cell. Linux/macOS
  retain strict handoff; a compatible Windows runner override through
  `EXOMA_WINDOWS_UPDATE_RUNNER` selects strict there too. A native Windows strict handoff is a
  mandatory release-staging gate in [RELEASE.md](../../RELEASE.md); `publish.yml` cannot
  enforce it. `tools/maintain/native_update_gate.py` runs the full manager/Python matrix
  on a native host and validates the commit-bound reports, but it is a maintainer-run
  check before tagging, not a publication barrier. Strict validation never accepts contained
  evidence. Production worker admission is unchanged: remaining job membership still
  refuses before mutation, and restrictive-host refusal remains covered by source tests.

## Validation

The targeted suites cover orphan retirement/startup races, admission persistence failures,
controlled frontend refusals and report mode/SHA validation. The `self-update` source suite
also covers the guardian matrix (exit 0/7 with post-reap
absence, group present, probe denied or failed, reap failure, missing observation,
owner/SIGTERM failure, non-EPERM kill error) with exact event ordering. Darwin and native
Windows strict behavior require commit-bound native evidence; contained coverage does not
certify either. Follow [RELEASE.md](../../RELEASE.md) for the remaining gates and the actual
candidate's run results. This note does not assert that those gates have already passed.
