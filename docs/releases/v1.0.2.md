# Exoma 1.0.2

Candidate preparation for an updater reliability patch. Tagging and publication remain
separate release actions; this page does not declare the candidate ready to publish.
The published `v1.0.1` tag and its package artifacts are retained.

## Changes

- `exoma update` displays its active stage, streams package-manager output, reports elapsed
  completion and prints a waiting heartbeat. Each package, refresh and check child has a
  configurable deadline through `--timeout SECONDS`; uv detection has a separate short limit.
- Inconclusive uv detection stops update instead of selecting pip. Optional dependency
  installation retains the timeout reason and does not recommend pip setup for it.
- Timeout and Ctrl+C attempt process-tree cleanup, skip later steps and retain incomplete
  install receipt/workspace recovery advice. Package-stage interruption reports uncertain
  package state rather than claiming that the package was unchanged.
- Windows cleanup attempts the existing native fallback when `taskkill` itself times out.
  An exited parent's remaining descendants also take the identity-aware native fallback
  when the Windows job object is unavailable. With an attached console, live-output
  children share that console; callers without one retain hidden child execution.
  Existing captured-output callers keep their default behavior; the updater opts into
  inherited output. Runtime dependencies remain stdlib-only.
- The test runner preserves its stdout contract and also writes failure summaries to
  stderr, keeping the actual assertion visible in the runtime's diagnostic tail.

See [installation and recovery](../installation.md#update) and the
[updater contract](../reference.md#detail-installer) for limits and usage.

## Compatibility and limits

Python 3.11+ is still required. Stored installer choices and the package-manager selection
policy are retained. Updates remain noninteractive.

The defaults (10-second detection, 900 seconds per child step, 15-second heartbeat) are
operational policy, not measured upper bounds on downloads or migrations. Increase
`--timeout` for slower work. The deadline does not bound filesystem preflight or cleanup;
Windows descendant cleanup remains best-effort where job assignment or access fails.
A timeout can interrupt partially completed package or filesystem changes.

The original reported stall has not been reproduced or attributed to a specific child.
This patch addresses confirmed missing deadlines and limited visibility; it does not
establish the cause of that historical incident.

When upgrading from an older release, the first invocation still runs the old updater.
Use the direct package-manager recovery sequence if that invocation hangs; run update
again under the new version to exercise the new supervisor.

The full source and Chromium runs above supersede the earlier 606.6-second and
83.7-second results, which preceded the follow-up repairs. The records are local,
pre-commit evidence; CI and staging still need to validate the final committed SHA.
This documentation-only update followed those runs and does not constitute another
execution of them.

The validation covers the following behavior and limitations:

- An opt-in artifact test installs the published 1.0.1 wheel into disposable uv tool,
  executable, cache, agent-home and workspace directories. Its SHA-256 was checked against
  PyPI metadata (`0289447449d7a52f0599110c1c28dfaaaf80f50eaa60ca95c51ce6916b3e1fa9`).
- The old updater returned exit 1 at the package stage. A direct-manager inspection found
  the candidate installed; the documented direct-manager upgrade, configuration refresh
  and installation check completed. This is a validated recovery path, **not** a passing
  old-updater transition, and it does not attribute the original historical stall.
- A subsequent invocation under the installed candidate returned exit 0 through the new
  supervisor, workspace refresh and installation check. This second package step was a
  no-op; timeout/cancellation behavior is exercised with real deterministic child fixtures.
- Follow-up regressions exercise an exited parent with no Windows job assignment and
  retain the actual optional-install detection timeout. A hidden private Windows console
  checks stdout/stderr while the child is alive, sends an OS-generated Ctrl+C event and
  verifies exit 130 plus descendant termination. The console test first exposed missing
  child output with `CREATE_NO_WINDOW`; sharing an attached console addresses that failure.
- An earlier full-suite run rejected the indirect subprocess kwargs under the existing
  `hidden-spawn` guard. Console inheritance is now an explicit option on the recognized
  `hidden_run_kwargs()` helper. The guard and attached-console regressions both pass;
  the full-source result above includes this correction.

The candidate wheel used for the latest isolated artifact check has SHA-256
`2fd85a062151d77822f7f68c01508c49cb7169b39236dc802c4eb80d442c7ff9`.
Its passing smoke result includes the documented manual recovery from 1.0.1, followed
by the installed candidate updater and installation check returning exit 0.

To repeat the artifact check, build the candidate wheel, set `EXOMA_UPDATE_UPGRADE_SMOKE=1`
and `EXOMA_UPDATE_WHEEL` to its absolute path, and run the `self-update` suite through the
project runtime. It downloads only the baseline wheel/metadata; package resolution uses
a local wheelhouse. `EXOMA_UPDATE_SMOKE_REPORT` optionally names a JSON results artifact.
Without the opt-in, `self-update` runs its normal regression checks.

The runtime records the selected commands, durations, outcomes and reuse identities.
Before publication, follow [RELEASE.md](../../RELEASE.md), including the supported OS/Python
CI matrix, distribution smoke checks, real-provider E2E, real-use review and companion
staging. The standalone local E2E command is not in this workspace's test allowlist and
remains a release gate. Source tests do not establish deployed-hook or live-provider
behavior. No tag, push, publication or companion-repository staging is part of this patch.
