# Exoma 1.0.0b1

> **Historical pre-release (superseded).** Exoma `1.0.0b1` was the pre-release ahead of `1.0.0` (superseded by `1.0.0` and later releases up to `1.3.0`). For current installation instructions, see [installation](../installation.md).

A pre-release of 1.0.0, published so the release could be tried on real work before it became
the version `pip install exoma` and `uv tool install exoma` picked. Its contents are the 1.0.0
release: what changed, how to upgrade from 0.3.0 and the known limitations are in
[the 1.0.0 notes](v1.0.0.md). Nothing here is a separate feature.

## Installing the pre-release (historical)

At the time of `1.0.0b1`, installers chose `0.3.0` unless the pre-release was explicitly requested:

```bash
uv tool install exoma==1.0.0b1          # or: uv tool install --prerelease allow exoma
python -m pip install --pre exoma       # or: python -m pip install exoma==1.0.0b1
exoma install
```

A uv tool installed with `exoma==1.0.0b1` kept that requirement, so `exoma update` (which
ran `uv tool upgrade exoma`) stayed on `1.0.0b1` rather than moving to a later release. Upgrading
to `1.0.0`+ required installing by name (`uv tool install --force exoma` or
`python -m pip install --upgrade exoma`), then `exoma install`. On a pip install, `exoma update`
ran `pip install --upgrade exoma` without `--pre`. Going back to `0.3.0` required installing it by
name (`uv tool install --force exoma==0.3.0` or `python -m pip install exoma==0.3.0`) and running
`exoma install` again.

## Release tooling

- `tools/maintain/stamp_version.py` reads a PEP 440 pre-release suffix (`a`, `b`, `rc`) as
  part of the version. It used to match only `X.Y.Z`, so stamping `1.0.0b1` a second time wrote
  `1.0.0b1b1` and `--check` failed. The runtime compares versions only for equality, so a
  pre-release string needs nothing else.
