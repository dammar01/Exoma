# Exoma 1.1.0

Candidate preparation for native host workflows and browser verification that can run
from preparation through execution and review in one invocation. This page describes
the candidate; promotion to `main`, final consumer staging, tagging and publication
remain separate release steps.

## Native host workflows

- Codex receives native skills and a host-specific main-agent contract, including the
  authoritative session binding and runner instructions. Installer migration and doctor
  checks recognize the rendered host instructions and detect drift.
- Shared host rendering aligns verification routing and evidence handling across Codex,
  Claude Code, OpenCode and Agy. Session binding and rendered-instruction integrity
  checks are stricter; refresh the installed host configuration and upgrade existing
  workspaces when moving to this release.

See [native command rendering and Codex migration](../reference.md#native-command-rendering-and-codex-migration)
and [workspace upgrade](../reference.md#workspace-upgrade).

## Verification preparation and routing

- The additive `verify-prepare` command centralizes verification request preparation and
  returns typed diagnostics for malformed requests or test policy. `execute-end`
  guidance points to the preparation path while retaining `verification: not_run`
  until verification actually runs.
- Shared prompts apply the same severity, origin and scope routing. Blocking findings,
  escalations, notes and unverified coverage remain distinct.
- Test-command policy fails closed: a malformed allowed prefix invalidates the allowed
  prefix set instead of leaving a partially accepted policy.
- POSIX launcher fixtures and migration regressions cover the host and workspace
  transitions. These tests do not replace checks of installed hooks on a real host.

See [verification mode](../reference.md#verify-mode) and
[runtime contracts](../runtime-contracts.md).

## Browser verification

- `verify-browser` accepts additive `phase: "auto"` orchestration: draft the spec, run
  the browser player and review its result in the same invocation. Existing explicit
  draft/run requests remain supported.
- Automatic execution uses the draft produced by that invocation; it does not silently
  borrow an older draft. Invalid drafts, unavailable credentials and required origin or
  request approvals still stop the flow.
- Stage usage and continuation handling preserve the preparation, player and review
  evidence needed to explain a result.

See the [browser verification contract](../runtime-contracts.md#verify-browser).

## Codex compatibility

The preferred tested Codex CLI baseline is `0.168.0`. Reviewer-context support retains
the previously tested `0.163.0`; provider CLI versions are independent of the Exoma
package version.

On Windows, the live probe using Codex `0.168.0` and `gpt-6.1-sol` completed fresh and
resumed turns with shell and file-edit writes refused, the original thread preserved,
and JSONL usage available. The shipped `auto_review.extra_policy` was accepted as a
string and rejected as a number. The probe now requires completed turns and tool
evidence, and an explicitly enabled probe fails when its CLI is unavailable.

This is Windows compatibility evidence, not a claim of live testing on every supported
OS. The probe's journal fallback recognizes Code Mode patch-call text; canonical
file-change events require failed status. Neither check independently eliminates every
possible misleading tool-output shape. Those verification limitations remain recorded
separately from the observed live result.

See [provider releases](../reference.md#provider-releases) for the opt-in probe and
the distinction between tested baselines and updater pins.

## Windows process cleanup

When a Windows job object is unavailable, bounded subprocess supervision now pins
descendants observed while their parents are still present. Cleanup can reach those
process generations even after a venv redirector or intermediate interpreter exits.
A second ancestry snapshot checks each opened handle before it is accepted; unknown
identities and unrelated reused PIDs do not grant permission to terminate anything.
Native termination waits have one bounded completion window across retained handles.

The regression fixture acknowledges the actual worker interpreter as well as its
launcher, checks native exit status, and reports ancestry and generation diagnostics
on failure. Deterministic cases cover disappearing parents, PID reuse, unavailable
identity, access denial and incomplete termination. Exit codes, captured output,
inherited output, heartbeat, timeout and cancellation contracts are retained.

Fallback tracking remains best-effort polling, not complete process containment: an
unobserved branch can still disappear between snapshots. Job assignment and native
permissions can also be unavailable. These limits are not relaxed by a passing test.

## Candidate validation and release gates

The earlier CI and agent-workflow staging evidence applies to commit `b39cc7a`, before
this version preparation. It must not be presented as exact-commit evidence for the
final release candidate.

Local release checks and environment details are recorded in the working session's
runtime artifacts. Source suites, real Chromium smoke, local and delegated provider
E2E, and the wheel in a clean environment cover different layers. An unavailable,
failed or skipped layer is recorded explicitly; a successful exit with skipped checks
does not prove that layer was exercised.

Initial Windows validation on 2026-11-13 failed the `exited-fallback` assertion under
the checkout venv (Python 3.13.11), while standard Python passed. Added diagnostics
confirmed a surviving worker with a matching creation identity and an unsignaled
native handle after the intermediate interpreter had exited; the final root snapshot
was empty. This observation led to the retained-descendant cleanup described above.
Keep the original failed receipts alongside subsequent checks. Earlier standard-only
passes and pre-change wheel checks are not acceptance evidence for this runtime change.

Before tagging, follow [RELEASE.md](../../RELEASE.md): publish the prepared candidate to
`main`, wait for CI, and stage the exact final commit in agent-workflow. Refresh the
consumer pin and receipt when the candidate SHA changes. Pushing the annotated tag
starts the publication workflow; this preparation does not perform that action.
