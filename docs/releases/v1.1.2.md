# Exoma 1.1.2

Candidate preparation for the macOS cleanup failure observed while publishing v1.1.1.
This page does not certify native release acceptance or publication.

## Changes

- **Coherent Darwin inventory.** Cleanup reads process status, microsecond start time,
  native parent and lifetime identifiers from one combined libproc record. The query
  includes zombie processes and does not require an executable path. Live-process
  identity and executable verification keep their existing semantics.
- **Conservative fallback.** A denied or unavailable combined query retains independent
  native lineage when readable. Missing identity remains explicit uncertainty; equal
  coarse `ps` timestamps and PPID 1 do not prove that a process is unrelated. Terminal
  ancestry stays in the ownership graph because an exited parent can leave surviving
  descendants. Unknown, reused or owned ancestry still prevents cleanup acceptance.
- **Bounded diagnostics.** Cleanup evidence includes an allowlisted numeric native
  status alongside the existing bounded generation/query diagnostics.

The shared ownership classifier also governs delegated-worker completion and cancellation.
There is no provider-adapter or public result-contract change in this candidate.

## Validation

### Enumeration identity correction and native validation

[CI run 44269192255](https://github.com/dammar01/Exoma/actions/runs/44269192255),
on commit `3e77085913617ca09b1be9e791ca3eeda8c46218`, failed its macOS/Python 3.13/pipx
strict cell. A-to-B succeeded. The separate no-op completed package work and probe
execution, but probe owner cleanup retained four rows after both zombie-inclusive
native identity queries returned ESRCH. Native initial identities were available;
current rows retained only coarse `ps` timestamps. Zombie-inclusive enrichment does
not close the earlier enumeration/query interval. Release acceptance remains pending.

The manual **Darwin inventory capability** workflow compiles an investigation-only
helper against the current runner SDK. It measures native record layout and tests
enumeration-time start data, later disappearance, and the counterexample of a vanished
parent with a surviving escaped child. Its report records OS version/build, kernel and
commit; workflow logs identify the runner image. A newer runner cannot retrospectively
certify the failed image. Compilation,
ABI and permission failures remain failures with preserved evidence.

Native [probe run 44284715093](https://github.com/dammar01/Exoma/actions/runs/44284715093)
on `9902ec3` measured the ARM64 layout and passed its controlled SDK observations.
Based on that measurement, the candidate adds a standalone `ctypes` process-table
reader for one measured ARM64, little-endian, 64-bit layout. It checks capability
through a selected-self native query rather than a kernel/build whitelist: exactly one
648-byte filled record must match independent libproc identity before and after capture.
Size-query padding cannot establish the stride; changed/ambiguous identity, parent or
status refuses the check. Real ABI changes can still require validation and maintenance.
It retains enumeration-time generation/parent/status when later lookups return ESRCH.
Combined enrichment must match the captured generation; lineage-only enrichment
requires a matching follow-up generation. Contradictions remain cleanup failures.
Unsupported process architectures/byte order/pointer widths keep the previous collector.
Errors after attempting the ARM64 capability check stop the operation instead of silently
downgrading native evidence. Ownership classification is unchanged.

No production compiler dependency is added. Schema-2 capability reports now require
production/SDK comparison, full-table production decoding and a controlled lineage-only
binding case. Baseline [schema-2 run 44298596214](https://github.com/dammar01/Exoma/actions/runs/44298596214)
on `a588be9` passed production/SDK comparison and cleanup under the previous build guard.
It does not certify the new capability guard. A successful capability
report is still not update release acceptance.
See [the capability contract](../runtime-contracts.md#darwin-inventory-capability-investigation).

Portable capability-contract tests exercise report validation and failed-run artifact
handling; they do not establish a native SDK/ABI result.

Existing runtime regressions cover the native structure decoder and zombie-inclusive
query, selected-self capability agreement/failure, terminal foreign lifetimes,
permission-restricted lineage fallback, unknown
processes and reused/owned ancestry. Worker lifecycle checks exercise completion,
retained cleanup uncertainty and subsequent update admission using the shared owner.
