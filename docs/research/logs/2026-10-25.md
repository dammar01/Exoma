# Research log — 2026-10-25

A research-period snapshot covering 2026-10-05 to 2026-10-25: what the 3.8.x real use showed about the split between the main agent and the second agent, how development was held while that was measured, and the literature and method notes that came out of an audit of the research corpus. The current status of claims lives in the linked records, not here.

## What the 3.8.2 real use shows, and in which scope

[CASE-028](../real-cases/CASE-028-real-use-of-3-8-x-context-split.yaml) records 13 coding tasks of 3.8.2 on two projects. The delegation happened: every task delegated, with a median of 6 calls. The second agent read a median of about 1.03M fresh tokens per task, and about 14.6k tokens came back to the main agent.

That is a context-allocation figure, not a cost figure. The second agent's tokens are spent either way, and nothing says the main agent would otherwise have read the same material.

The same record shows that the split did not run the way the digest-first rule describes it. The delegate's full output was read whole on 67 of 123 runs, and almost all of the main agent's own gathering came after its first delegated run.

The outcomes (9 of 13 solved, 6 clean, 3.4 verify and 1.8 fix follow-ups per task) are recorded beside these figures. They are not explained by them: there was no arm without delegation and no digest-only arm.

Four statements are kept apart:

```text
delegation occurred                   observed (CASE-028)
the split ran as designed             not observed: full output read back on about half the runs
task quality                          observed outcomes, no comparison
system efficiency                     not measured: saved context is not saved cost
```

The hypothesis these figures were collected for, a low primary context through digest-only delegation (draft H-017), remains untested. Its treatment did not occur.

## Scope corrections made during the audit

Figures from the same local data directory had started to circulate without their scope. The audit found three problems:

- The aggregate of 18 tasks pools 3.8.1, whose sessions were the maintainer's smoothness testing, with 3.8.2 work. So does the per-project block a later note quoted (about 973k saved tokens for one project). CASE-028 uses the 3.8.2 block only.
- The `digest_only` field in the behaviour data is never set by the script that writes it. Its zeros are not a measurement.
- Two scripts over the same sessions count different task totals (13 and 15 for 3.8.2). They are not reconciled.

The 3.7.3 snapshot in the same directory is a different task set. It is not a baseline for a version comparison without matching the tasks.

## Development held while the split is measured

After 3.8.2 the general feature freeze was replaced by controlled development (draft DEC-063, not implemented as a record). The proposed boundary:

- Held: changes to orchestration, defaults, and the digest, since these are the variables H-016 and H-017 need to stay fixed.
- Allowed: reproducible bug fixes, compatibility fixes, diagnostics, regression tests, documentation, and scoped capabilities.

This applies the rule already in [CHARTER.md](../CHARTER.md) §6–§8 to a period: a mechanism is added for a research variable, not because another platform has it. No separate decision is recorded for it here.

## Context allocation and the extended-mind lens

[LIT-002](../literature/LIT-002-the-extended-mind.yaml) (Clark and Chalmers, 1998) was read against the full text. It gives the split a vocabulary, not a design origin.

- Its socially extended case is the closest analogue: one agent's states play the role of another's memory, given trust, reliance, and accessibility, and the coupling is carried by language.
- Its criteria give a precise name to digest-only use: acting on the digest with automatic endorsement.
- Its Twin Otto case names the matching risk: a wrong entry trusted without checking.

The maintainer's own reading is the weaker one, that the coupled tool scaffolds thinking rather than being part of it. For this project the two readings are an empirical question, which [RQ-01](../questions/RQ-01-net-value-of-external-exploration.yaml) already asks: when does the stronger coupling pay?

A related distinction was added to draft H-017. What reaches the main agent has three layers:

1. the second agent's synthesis, which is already its final answer;
2. deterministic runtime packaging;
3. any further semantic summary.

The maintainer's position is that the third layer is not needed by default. Whether the runtime applies it today was not checked.

## Current position

The 3.8.2 data establishes that delegation was used heavily and that its output was read back often. It does not establish whether keeping the main agent's context low, by acting on the digest alone, would change task outcomes.

That needs the digest-only arm of draft H-017, a retrieval the runtime does not enforce today. It also needs a cost measure that counts the second agent's tokens rather than subtracting them.
