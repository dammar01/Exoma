# Release procedure

One version number, one tag, one manifest, one wheel. Every step below is a command that
already exists in the repo — this file only fixes their order and makes skipping one visible.

## Where the version lives

`TOOL_VERSION` in `src/exoma/config/settings.py` is the single source. Everything else
derives from it (named by symbol, not line, so the list survives edits to those files):

- `CONFIG_VERSION` — `src/exoma/core/workspace/workspace_paths.py`
- `COMPONENT_VERSIONS` — `src/exoma/config/settings.py`
- `.workflow/config.json` `version` — `default_config()` in
  `src/exoma/core/runtime/config_defaults.py`, backfilled on upgrade by
  `merge_config_defaults()` in the same file
- `.workflow/config.json` `runtime.tool_version` and `runtime.runtime_version` —
  `merge_config_defaults()` in `src/exoma/core/runtime/config_defaults.py`
- `pyproject.toml` `version` — a static copy, because `uv_build` reads no dynamic version;
  rewritten by `tools/maintain/stamp_version.py`
- documentation banners in `README.md`, `docs/reference.md`, each provider bundle's instruction
  files, `CLAUDE.md` and skill files — rewritten by `tools/maintain/stamp_version.py`, whose
  `TARGETS` table names every anchored line
- `src/exoma/_bundle/manifest.json` — regenerated by `tools/maintain/gen_manifest.py`

`state.json` is deliberately NOT on that list. Its `version` is the literal `1` in
`default_state()` in `src/exoma/core/runtime/config_defaults.py` — a state-schema number
that changes when the state layout changes, never when the tool is released.

Never edit a version by hand anywhere but `src/exoma/config/settings.py`. The stamp targets
are an explicit list precisely so that an unrelated semver in prose is not rewritten by
accident.

## Cutting a release

1. **Bump.** Edit `TOOL_VERSION` in `src/exoma/config/settings.py`.

2. **Stamp.** Propagate it and confirm nothing was missed:

   ```
   python tools/maintain/stamp_version.py
   python tools/maintain/stamp_version.py --check
   ```

   `--check` fails when a target file is missing, not only when a banner is stale. A new
   provider bundle adds a target by existing (the `PROVIDER_BUNDLES` loop that extends
   `TARGETS`), so a provider declared in `src/exoma/config/providers.py` without its
   `src/exoma/_bundle/config/providers/<name>/` instruction file fails here. That is the check working.

3. **Manifest.** Regenerate and confirm:

   ```
   python tools/maintain/gen_manifest.py
   python tools/maintain/gen_manifest.py --check
   ```

   The manifest carries a sha256 and byte count per shipped file. It is what makes an
   install verifiable after the fact — `core/audit/bundle_integrity.py` compares against it.

4. **Lock.** `uv lock`, so `uv.lock` names the new version.

5. **Release notes.** Write `docs/releases/v<version>.md` (`docs/releases/v0.1.0.md` is the
   format) and add one row to the index table in `CHANGELOG.md` — version, link, a one-line
   theme. The index stays an index: detail goes in the release file, and behavior is linked
   to `docs/reference.md` / `docs/runtime-contracts.md` rather than restated.

6. **Test.** This is the tag gate. All of it, in this order:

   ```
   uv run python tests/run.py
   WORKFLOW_E2E_SMOKE=1 uv run python tests/run.py --only e2e-smoke   # real Chromium, needs the e2e extra
   uv run python tools/e2e/e2e.py
   uv run python tools/e2e/e2e.py --full --provider <opencode|codex|agy|claude> --model <id>
                                             # spends real quota, needs that provider installed;
                                             # agy takes the variant id (e.g. gemini-3.8-flash-low)
   ```

   Then **the wheel in a clean environment**: `uv build`, install `dist/exoma-<version>-py3-none-any.whl`
   into a fresh venv, and run `exoma --version`, `exoma install --dry-run` (with `HOME`,
   `USERPROFILE`, `AGENT_HOME` and `EXOMA_HOME` pointed at a temp directory), `exoma init` in a
   temp project, and its `.workflow/inspect.sh --session dist-smoke`.

   Self-update on all three OSes additionally requires an actual candidate A-to-B transition:

   ```powershell
   python tests/run.py --only self-update --traceback --update-artifacts handoff
   ```

   Run it from a terminal/host that permits an independent worker. A restrictive supervisor
   must refuse handoff before package mutation; protocol-only tests inside that supervisor
   do not replace the artifact gate. The gate builds disposable A/B wheels containing the
   candidate updater, polls journal files after A exits, and requires B plus refresh/check
   and preserved user data. Manual recovery or a package no-op cannot satisfy it. CI runs
   this gate on Linux/macOS for both CI Python versions and uv/pipx/pip venvs; operation logs are preserved with the result artifact. On GitHub-hosted Windows CI skips only this handoff step (the runner keeps the helper inside an outer job); setting the JSON repository variable `EXOMA_WINDOWS_UPDATE_RUNNER` to supported Windows runner labels re-enables it there.
   **The handoff on a native Windows host (all three managers, both Python versions) is a
   mandatory release-staging gate**: run the command above there before tagging and record
   the result. `publish.yml` cannot enforce it, so it depends on this step being followed.
   Run the whole matrix on each native host from a clean checkout of the exact commit to tag:

   ```powershell
   python tools/maintain/native_update_gate.py matrix --python-311 <python3.11> --python-313 <python3.13>
   ```

   It runs the command above for uv, pipx and pip under both interpreters, writes one
   commit-bound report per cell under the git-ignored `.workflow/release-evidence/`, and
   exits nonzero if any cell is missing or does not qualify. Keep that directory with the
   release record; `native_update_gate.py validate <dir> --commit <sha>` rechecks it later.
   `--update-artifacts contained` exercises the real package/refresh/check transition in
   disposable fixtures under a restrictive test supervisor. It relaxes only that fixture's
   inherited-job assertion; it does not verify independent-worker survival and cannot
   replace the `handoff` release gate.

   Then **real use**: the maintainer runs the changed commands on an actual project and
   finds no safety problem — no write the guard should have refused, no credential in an
   artifact, no data touched outside the test account. A wrong or overly strict verdict is a
   bug to record, not a gate failure; an unsafe run is.

   `e2e-smoke` is the only step that drives a real browser; CI skips it. `--full` is the only
   step that exercises a real delegated call end to end. Skipping either means the release
   never ran against that layer — record the decision in the release notes rather than
   leaving it implied.

6b. **Stage in agent-workflow.** Push the candidate to `main`, wait for CI, then point
   agent-workflow's Exoma dependency at that commit and run its staging suite there,
   delegated end-to-end run included. A failure is fixed here and the candidate re-staged;
   nothing is patched inside agent-workflow. See
   [docs/development.md](docs/development.md#staging-a-release-in-agent-workflow).

   This remains an engineering release gate. Harnesses, delegated E2E, and integrity checks
   for research records maintained there are required by the staging procedure; successful
   scientific validation or an answered research question is not a prerequisite for
   implementation or release acceptance. An Exoma feature does not require its own research
   record. See the
   [Development and Research Relationship](docs/development.md#development-and-research-relationship).

7. **Commit, then tag.** The tag points at the commit whose `stamp_version --check` and
   `gen_manifest --check` both passed:

   ```
   git tag -a v<version> -m "Exoma v<version>"
   git push origin v<version>
   ```

8. **Publish.** Pushing the tag is the publish. `.github/workflows/publish.yml` runs all of
   `ci.yml` on the tagged commit, refuses a tag whose name does not match the built wheel's
   version, and uploads the `dist/` artifact CI built and smoke-tested through PyPI Trusted
   Publishing. Nothing is rebuilt between the gate and the upload, and no token exists.

   One-time setup before the first tag: on PyPI, add a trusted publisher for this
   repository with workflow `publish.yml` and environment `pypi` (a pending publisher, if
   the project does not exist yet); on GitHub, create the `pypi` environment, with a
   required reviewer if a human should approve each upload.

   Fallback when the workflow cannot run, from the tagged commit:

   ```
   uv build
   uv publish
   ```

   with the token passed as `UV_PUBLISH_TOKEN` and never committed. A PyPI version cannot
   be re-uploaded, only yanked: a bad upload costs the number.

9. **Verify the tag reproduces.** From a clean checkout of the tag:

   ```
   python tools/maintain/stamp_version.py --check
   python tools/maintain/gen_manifest.py --check
   uv run python tests/run.py
   ```

   All three must pass with no working-tree changes. If `gen_manifest --check` reports
   drift here, the tag shipped a manifest that does not describe its own bundle — retag.

## What CI already covers

`.github/workflows/ci.yml` runs steps 2, 3 and 6 (without `e2e-smoke`, `--full`, or real
use) on every push and pull request, on Linux, Windows and macOS with Python 3.11/3.13.
Its `dist` matrix uses Python 3.11 (the package floor) and 3.13 on all three OSes: the wheel
smoke covers a clean install, version, noninteractive host install, init and generated
inspect; a separate clean venv installs the sdist and checks import, bundle presence and
version. Only Ubuntu with Python 3.13 uploads the publish artifact. The full source suite is not rerun against either installed artifact.

CI bumps nothing and tags nothing. A pushed tag triggers `publish.yml` (step 8); everything
else — deciding the number and running steps 1, 4, 5, 6b, 7 and 9 — is still a human's. The delegated end-to-end run
(`.github/workflows/e2e-full.yml`) is manual and covers no release step: it exists to spend
quota deliberately, not on a schedule.

## Known gap

The runtime has no third-party dependencies, so `uv.lock` pins only the optional `e2e`
extra (Playwright). Reproducibility here means "the same bundle bytes for the same tag",
verified by step 9, plus a wheel built by a pinned `uv_build` range — not a pinned
toolchain. The Python version is pinned only in CI.
