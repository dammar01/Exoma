# Release procedure

One version number, one tag, one manifest. Every step below is a command that already
exists in the repo — this file only fixes their order and makes skipping one visible.

## Where the version lives

`TOOL_VERSION` in `config/settings.py` is the single source. Everything else derives
from it (named by symbol, not line, so the list survives edits to those files):

- `CONFIG_VERSION` — `core/workspace/workspace_paths.py`
- `COMPONENT_VERSIONS` — `config/settings.py`
- `.workflow/config.json` `version` — `default_config()` in
  `core/runtime/config_defaults.py`, backfilled on upgrade by `merge_config_defaults()`
  in the same file
- `.workflow/config.json` `runtime.tool_version` and `runtime.runtime_version` —
  `merge_config_defaults()` in `core/runtime/config_defaults.py`
- documentation banners in `README.md`, `docs/reference.md`, `dist/config/*/AGENTS.md`,
  `dist/config/claude/CLAUDE.md`, and the skill files — rewritten by
  `tools/maintain/stamp_version.py`, whose `TARGETS` table names every anchored line
- `dist/manifest.json` — regenerated by `tools/maintain/gen_manifest.py`

`state.json` is deliberately NOT on that list. Its `version` is the literal `1` in
`default_state()` in `core/runtime/config_defaults.py` — a state-schema number that changes when the
state layout changes, never when the tool is released. It used to be listed here, and a
releaser chasing it found a file that no bump is supposed to touch.

Never edit a version by hand anywhere but `config/settings.py`. The stamp targets are an
explicit list precisely so that an unrelated semver in prose is not rewritten by accident.

## Cutting a release

1. **Bump.** Edit `TOOL_VERSION` in `config/settings.py`.

2. **Stamp.** Propagate it and confirm nothing was missed:

   ```
   python tools/maintain/stamp_version.py
   python tools/maintain/stamp_version.py --check
   ```

   `--check` fails when a target file is missing, not only when a banner is stale. A new
   provider bundle adds a target by existing (the `PROVIDER_BUNDLES` loop that extends `TARGETS` in
   `tools/maintain/stamp_version.py`), so a provider
   declared in `config/providers.py` without its `dist/config/<name>/AGENTS.md` fails here.
   That is the check working, not a false alarm.

3. **Manifest.** Regenerate and confirm:

   ```
   python tools/maintain/gen_manifest.py
   python tools/maintain/gen_manifest.py --check
   ```

   The manifest carries a sha256 and byte count per shipped file. It is what makes an
   install verifiable after the fact — `core/audit/bundle_integrity.py` compares against it.

4. **Release notes.** Write `docs/releases/v<version>.md` (`docs/releases/v3.7.3.md` is the
   format) and add one row to the index table in `CHANGELOG.md` — version, link, a one-line
   theme. The index stays an index: detail goes in the release file, and behavior is linked
   to `docs/reference.md` / `docs/runtime-contracts.md` rather than restated. Do not create
   `prompt/v<version>/`: `prompt/` is a historical archive that ends at v3.7.2.

   **Research records.** Replace every `uncommitted` in a decision's
   `implementation.commits` with the hash of the commit that carries it, then:

   ```
   python tools/maintain/check_research.py --strict --git
   ```

   `--strict` refuses `uncommitted`; `--git` checks every named commit exists. The same
   check fails when the README inventory or `docs/research/questions.md` is stale; run it
   with `--write-inventory` after adding or promoting a record. When
   `docs/research-drafts/` exists locally, also run `--drafts`: CI has no drafts to check.

5. **Test.** This is the tag gate. All of it, in this order:

   ```
   python tests/run.py
   WORKFLOW_E2E_SMOKE=1 python tests/run.py --only e2e-smoke   # real Chromium, needs --with-e2e
   python tools/e2e/e2e.py
   python tools/e2e/e2e.py --full     # spends real quota, needs a configured provider
   ```

   Then **real use**: the maintainer runs the changed commands on an actual project and
   finds no safety problem — no write the guard should have refused, no credential in an
   artifact, no data touched outside the test account. A wrong or overly strict verdict is a
   bug to record, not a gate failure; an unsafe run is.

   `e2e-smoke` is the only step that drives a real browser; CI skips it. `--full` is the only
   step that exercises a real delegated call end to end. Skipping either means the release
   never ran against that layer — record the decision in the release notes rather than
   leaving it implied.

   Research validation is not a tag gate. A tag may ship with records `observed` or
   `not_validated`, provided their disposition says so honestly
   (`docs/research/CONTRACT.md` §14).

6. **Commit, then tag.** The tag points at the commit whose `stamp_version --check` and
   `gen_manifest --check` both passed:

   ```
   git tag -a v<version> -m "agent-workflow v<version>"
   git push origin v<version>
   ```

7. **Verify the tag reproduces.** From a clean checkout of the tag:

   ```
   python tools/maintain/stamp_version.py --check
   python tools/maintain/gen_manifest.py --check
   python tests/run.py
   ```

   All three must pass with no working-tree changes. If `gen_manifest --check` reports
   drift here, the tag shipped a manifest that does not describe its own `dist/` — retag.

## What CI already covers

`.github/workflows/ci.yml` runs steps 2, 3, and 5 (without `e2e-smoke`, `--full`, or real
use), and the research check without `--strict`, on every push and pull request, on Linux
and Windows.

CI bumps nothing, tags nothing, publishes nothing. A release still requires a human to decide
the number and run steps 1, 4, 6, 7. The delegated end-to-end run
(`.github/workflows/e2e-full.yml`) is manual and covers no release step: it exists to spend
quota deliberately, not on a schedule.

## Known gap

There is no reproducible-build guarantee beyond the manifest hashes: the runtime has no
lock file because it has no third-party dependencies (no `requirements.txt`, no
`pyproject.toml`). `requirements-e2e.txt` (Playwright, optional extra) and
`requirements-dev.txt` (PyYAML, maintainer checks only) are pinned and never imported by the
core runtime. Reproducibility here means "the same `dist/` bytes for the same tag",
verified by step 7 — not a pinned toolchain. The Python version is pinned only in CI.
